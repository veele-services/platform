## Evidence model

Statuses:

- `proven`: source trace shows route/component/action/API, permission or identity guard, tenant context, database mutation, downstream read, and at least static/source test coverage for the contract.
- `partially connected`: the main mutation exists, but one or more downstream consumers, events, transactions, module checks, or tests are incomplete.
- `disconnected`: a canonical state mutation exists but expected event/outbox/downstream linkage is absent.
- `unsafe`: source trace shows a security, tenant-boundary, financial, or cross-surface consistency defect.
- `unproven`: UI or schema exists, but route-to-mutation-to-consumer proof was not established from source.

Every row below is source-level evidence only unless explicitly described as tested. No database, RLS, storage, provider, browser, staging, DNS, SMTP, Mollie, Supabase, VPS, or deployment runtime proof was collected.

## Explicit black-hole findings

- Status changes without downstream records: report approval can return success while invoice proposal creation failed; backoffice all-status override can set terminal/financial assignment statuses without side-effect events.
- Notification success without canonical parity: personnel report submission sends direct email without `report_submitted` event/outbox; payment reminder sends direct email without durable `payment_reminder` event; manual payment and Mollie webhook paid transitions do not emit the same `invoice_paid` event as `markInvoicePaid`.
- UI revalidation isolated to one app: assignment status override and several payment/report flows refresh only the initiating Next app path.
- Record exists but another surface filters it out: draft invoices are hidden by customer invoice list/PDF but can appear in customer assignment detail invoice join.
- Cross-tenant data exposure: backoffice activity log lacks tenant filtering, and multiple assignment/auth mutation paths accept ids without current-tenant predicates.
- Auth side-effect before notification proof: password reset and invite flows can mutate Supabase Auth before email delivery succeeds.
- Candidate/suggested mistaken for confirmed assignment: no active defect proven; current personnel work-order reads use `assignment_personnel.status = assigned`, but selected/reserve-to-assigned conversion is unproven.
- Customer-visible status never advances: webhook/manual payment parity is inconsistent; customer payment result evidence is not proven without live Mollie/webhook runtime.
- Module-off or tenant suspension not rechecked by jobs: payment reminders check finance entitlement but not tenant runtime active/suspended/archive status.

## Testing classification

Existing coverage found during source audit is mostly static/source-contract and unit-style Node tests under `tests/*.test.mjs`. Some scripts describe runtime, staging, browser, database, RLS/storage, and provider gates, but they were not run for this documentation task. No command in this audit proves live runtime, database, RLS/storage, provider, browser, or deployment behavior.
